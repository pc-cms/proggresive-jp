# Controller protocol v1

Аппаратный controller_id — зарегистрированная device identity, привязанная к table_id. Отдельный physical block получает собственные credentials через pairing (в v1 только одно active управляющее device на стол, не параллельно отдельному terminal operator). Для совместного экрана и hardware adapter требуется утверждённая схема единственного command producer/lease.

Transport HTTPS API v1 + authenticated SSE. Команда:

```json
{"command_id":"UUID","operator_id":"unique-connection-owner","sequence":1,"op":"confirm","payload":{"table_id":"ID","round_id":"next_round_id","boxes":[1,3]}}
```

Ответ содержит тот же command_id, `{sequence,committed:true}`, round/participants. До отправки приобрести operator lease. При reconnect GET state, GET command status для неизвестного результата; повторить тем же ID/sequence. Следующий sequence только после committed. Не выполнять локальных денежных действий. Если sequence rejected, получить полное состояние, не переписывать ранее отправленное намерение автоматически новым номером.

Indicators = confirmed round boxes; pending approvals и winner = серверные claims/events; связь = успешный heartbeat/SSE с timeout. Лампочка отражает состояние, не подтверждает приём финансовой операции. После disconnect блокировать кнопки новых финансовых команд, показать fault, при reconnect заново применить полный state.

Simulator: `scripts/controller_simulator.py --url ... --token-file ... --ca ... --box 1`. Token file mode 0600, сертификат проверяется. Выполнять только на TEST installation; simulator действительно подтверждает test stake. Sequence/idempotency/lease покрыты API tests. Реальный USB/physical controller, GPIO, напряжения, распиновка и электрическая безопасность не проверены и не выбраны.

## Пилот с планшетом/телефоном вместо NumPad

Планшет или телефон может быть тонким интерфейсом выбора боксов и подтверждения, но не хранителем денежного раунда. Раунд, фонды, sequence, command ID и журнал остаются у сервера; USB LED остаётся подключённым к локальному mini-PC/gateway. И vendor LED, и custom LED должны отображать один подтверждённый снимок состояния, а не независимо трактовать нажатия.

До внедрения надо выбрать единственного command producer: либо браузер устройства, либо локальный gateway, через который идёт ввод. Два независимо paired устройства/оператора на одном столе текущая v1-схема не разрешает. Выбор авторизации gateway и поддержка нескольких экранов требуют отдельной реализации; простое открытие двух управляющих страниц не заменяет её. Credentials телефона не должны становиться USB-драйвером или получать произвольный доступ к сети/командам mini-PC.

При обрыве/отсутствии подтверждённой связи запрещены новые денежные действия. Последнее известное состояние ламп должно отличаться от подтверждённого текущего; конкретный безопасный fault-режим согласуется с протоколом контроллера. После восстановления применить полный серверный снимок, затем новые события. Рекламный ролик можно воспроизводить автономно только как отдельный информационный слой; он не должен скрывать отсутствие связи или изображать успешную ставку. Offline-кэш рекламы и USB adapter в этом репозитории не реализованы.

Приёмка на реальном пятибоксовом столе: сравнить vendor/custom LED для боксов 1–5; подтвердить одну ставку и сверить round ID/суммы; перезагрузить только экран; отключить сеть без сброса контроллера и проверить fault/no-new-bets; восстановить сеть и проверить полный снимок без дубликата ставки; отдельно проверить показ рекламы без сети. Нужны модель контроллера, документированный USB/serial протокол и физический доступ к стенду. Пока эти проверки не выполнены, совместимость LED/автономной рекламы не подтверждена.
